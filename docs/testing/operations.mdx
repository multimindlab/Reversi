This page tests what you need in order to run Reversi for other people: who may sign in, who gets told, what evidence you can
hand to an auditor, how long data is kept, where it may be sent, and where it lives. The first guide, [Manual testing](/testing),
covers the core product; do its section 5.1 and 5.2 first if you have never run the server.

Run everything from the **repository root**, in `bash` or `zsh`, after `npm install && npm run build`. Scratch files go in
`try/ops/` (delete the folder to start over). Services use ports 7800 to 7849 on `127.0.0.1` only; change them if they are busy.

<Note>
Every command and output below comes from a real run against this repository, in the order shown. IDs, timestamps and hashes
will differ on your machine. Slack, Teams, email, PagerDuty, Opsgenie and OpenTelemetry are exercised **only against fakes you
start on localhost**, never against the real services. The console is checked with `curl` (it is server-rendered HTML); open the
same URLs in a browser to see them drawn. See [Not covered here](#not-covered-here) for the full list.
</Note>

A block that starts with `# Terminal A` runs in its own terminal, which you leave running; every other block goes in your
working terminal, called B here. Stop a terminal with Ctrl-C when the text says so.

## 0. Setup

You need Node 22.13 or newer, Python 3, `curl`, `openssl` and `shasum`. The `psql` client is optional (section 9).

Manifests, a policy (an approval rule, secret detection and a `retention:` section) and one API key per role:

```bash
mkdir -p try/ops/manifests
cat > try/ops/manifests/tools.yaml <<'EOF2'
- tool: lookup_customer
  effect: read_only
  permission: customers:read

- tool: create_order
  effect: reversible
  permission: orders:write
  compensation:
    tool: cancel_order
    argument_map:
      order_id: $result.order_id

- tool: cancel_order
  effect: idempotent
  permission: orders:write

- tool: charge_card
  effect: compensable
  permission: payments:write
  compensation:
    tool: refund
    argument_map:
      charge_id: $result.charge_id
      amount: $args.amount
  audit:
    evidence_export: required

- tool: refund
  effect: idempotent
  permission: payments:write

- tool: delete_customer
  effect: irreversible
  permission: customers:admin
EOF2
cat > try/ops/policy.yaml <<'EOF2'
version: 1
rules:
  - id: big-charges
    match: { tool: charge_card }
    when: [{ path: $args.amount, op: gt, value: 100 }]
    action: require_approval
    reason: charges over 100 need a human
content:
  secrets: deny
retention:
  default_days: 30
EOF2
sha() { printf '%s' "$1" | shasum -a 256 | cut -d' ' -f1; }
AGENT=agent-$(openssl rand -hex 8); AUD=aud-$(openssl rand -hex 8); APPR=appr-$(openssl rand -hex 8)
OPS=ops-$(openssl rand -hex 8); ROOT=root-$(openssl rand -hex 8)
cat > try/ops/keys.json <<EOF2
[
  { "name": "order-agent", "role": "agent",    "key_sha256": "$(sha $AGENT)", "max_permissions": ["customers:read","orders:write","payments:write"] },
  { "name": "audrey",      "role": "auditor",  "key_sha256": "$(sha $AUD)" },
  { "name": "alice",       "role": "approver", "key_sha256": "$(sha $APPR)" },
  { "name": "dana",        "role": "operator", "key_sha256": "$(sha $OPS)" },
  { "name": "root",        "role": "admin",    "key_sha256": "$(sha $ROOT)" }
]
EOF2
```

The keys, the environment every terminal shares, and a few helpers: `rv` is the CLI, `j` calls the API with a key, `post` calls a
console page and prints its status and text, `login` signs a key in to the console and keeps the cookie in `try/ops/jar-NAME`.
Each new terminal starts with `. try/ops/.env.sh`.

```bash
cat > try/ops/.env.sh <<EOF2
AGENT=$AGENT; AUD=$AUD; APPR=$APPR; OPS=$OPS; ROOT=$ROOT
export HOOK_SECRET=$(openssl rand -hex 16)
EOF2
cat >> try/ops/.env.sh <<'EOF2'
export REVERSI_MANIFESTS=try/ops/manifests REVERSI_KEYS=try/ops/keys.json REVERSI_POLICY=try/ops/policy.yaml
export REVERSI_SIGNING_KEY=try/ops/signing.key REVERSI_DATA=try/ops/data
rv() { node packages/cli/dist/main.js "$@"; }
j() { curl -s -H "Authorization: Bearer $1" -H 'content-type: application/json' "${@:2}"; echo; }
msg() { sed -n 's/.*<main>\(.*\)<\/main>.*/\1/p' | sed -E 's#</(p|h1|h2|td|th|li|tr)>#  #g; s/<[^>]*>//g' | tr -s ' '; }
post() { curl -s -o try/ops/out.html -w "%{http_code} " "$@"; msg < try/ops/out.html; echo; }
login() { rm -f try/ops/jar-$1; curl -s -c try/ops/jar-$1 -o /dev/null -w "$1: login %{http_code}\n" --data-urlencode "key=$2" localhost:${3:-7800}/console/login; }
csrf() { curl -s -b try/ops/jar-$1 localhost:${2:-7800}/console/runs | grep -o 'name="csrf" value="[^"]*"' | head -1 | cut -d'"' -f4; }
kix() { curl -s -H "Authorization: Bearer $ROOT" localhost:7800/v1/keys | python3 -c "import sys,json;print([k['index'] for k in json.load(sys.stdin)['keys'] if k['name']=='$1'][0])"; }
pending() { curl -s -H "Authorization: Bearer $APPR" "localhost:7800/v1/approvals?status=pending" | python3 -c "import sys,json;print([a['id'] for a in json.load(sys.stdin)['approvals'] if a['run_id']=='$1'][0])"; }
EOF2
. try/ops/.env.sh; B=localhost:7800
```

```bash
rv validate $REVERSI_MANIFESTS
rv keygen try/ops/signing
```

Expect:

```text
ok: 6 tool manifests valid
wrote try/ops/signing.key and try/ops/signing.pub (key id d67bfe0ef2ea4b10)
```

## 1. Console modes

The console is **off by default**. Choose a mode with `REVERSI_CONSOLE` on the server, `--console` on the gateway, or
`console: { mode: … }` in `reversi.config.yaml`:

| Mode | Login | Who can reach it | Role |
|---|---|---|---|
| `off` | none | nobody: `/console` answers 404 | none |
| `open` | none | requests to `localhost` from the same origin only, on a loopback listener | fixed: `operator` by default, or `auditor` or `approver`; never `admin` |
| `login` | paste an API key or an OIDC access token | anyone who can reach the port and holds a credential | the credential's roles |

### 1.1 Off

```bash
# Terminal A
. try/ops/.env.sh
PORT=7800 node packages/server/dist/main.js
```

Expect: `reversi-server listening on http://127.0.0.1:7800 (6 tools, files store, console off)`.

```bash
curl -s -i $B/console | head -1
curl -s $B/console; echo
j $OPS $B/v1/status
```

Expect:

```text
HTTP/1.1 404 Not Found
The console is off. Start Reversi with REVERSI_CONSOLE=open (on your own machine, no login) or REVERSI_CONSOLE=login.
{"halted":null,"environment":"default","runs":0,"pending_approvals":0}
```

```bash
# Terminal A: press Ctrl-C
```

**What this proves:** with no setting the console does not exist, while the API works.

```bash
post -H 'Host: evil.example.com' http://127.0.0.1:7800/console/runs
CSRF=$(curl -s $B/console/approvals | grep -o 'name="csrf" value="[^"]*"' | head -1 | cut -d'"' -f4)
post -X POST -H 'Origin: http://evil.example.com' -d "csrf=$CSRF&reason=x" $B/console/halt
```

Expect:

```text
403 Not allowed The console in open mode only answers requests made from this machine to localhost. Use REVERSI_CONSOLE=login to serve it to other people.
403 Not allowed The console in open mode only answers requests made from this machine to localhost. Use REVERSI_CONSOLE=login to serve it to other people.
```

The open console is never admin, so the kill switch and publishing are refused even from the right origin with a valid CSRF
token. (The token sits on any page with a form; the approvals page has them.)

```bash
post -X POST -H "Origin: http://$B" -d "csrf=$CSRF&reason=x" $B/console/halt
post -X POST -H "Origin: http://$B" -d "csrf=$CSRF" $B/console/manifests/charge_card/approve
post -X POST -H "Origin: http://$B" -d "reason=x" $B/console/halt
```

Expect:

```text
403 Forbidden Your role does not allow this.
403 Forbidden Your role does not allow this.
403 Forbidden Invalid or missing CSRF token. Go back, reload the page and try again.
```

What it can do is what its role allows. As operator it can approve, and the ledger names it `local-console`:

```bash
ID=$(pending c-1)
post -X POST -H "Origin: http://$B" -d "csrf=$CSRF&note=looks+fine" $B/console/approvals/$ID/approve
j $APPR "$B/v1/approvals?status=approved" | python3 -c 'import sys,json;a=json.load(sys.stdin)["approvals"][0];print(a["status"],a["decided_by"])'
curl -s -o /dev/null -w "the API without a key: %{http_code}\n" $B/v1/status
```

Expect:

```text
303
approved local-console
the API without a key: 401
```

```bash

```

**What this proves:** open mode needs no credential but refuses any request that is not plainly your own browser talking to
`localhost`; it can never become admin; and it cannot be started where other people could reach it.

```bash

j $ROOT -X PATCH $B/v1/keys/$(kix audrey) -d '{"disabled":false}'
curl -s -b try/ops/jar-aud -o /dev/null -w "after enabling it again: %{http_code}\n" $B/console/runs
```

Expect:

```text

{"ok":true}

{"error":"missing or invalid API key"}
{"ok":true}

```

Leave Terminal A running for section 2.

**What this proves:** login mode needs a credential with a console role (agent keys are refused), pages and buttons follow the role,
a forged POST from a lower role is refused even with a valid CSRF token, and disabling a key ends its sessions without a restart.

## 2. API keys: file format, console, API, rotation, expiry

A key file is a JSON list. Each entry has a `name` (it becomes the actor in the ledger), `role` or `roles`, and `key_sha256` (the hex
SHA-256 of the key; the key itself is never stored). Optional: `max_permissions` (agents), `groups`, `tenant`, `not_before`,
`expires_at`, `disabled`, `allow_observe`. The server re-reads the file on `SIGHUP` or when it changes (checked every two seconds).
Terminal A from section 1.3 is still running.

```bash
j $ROOT $B/v1/keys | python3 -c 'import sys,json;[print(k["index"],k["name"],k["roles"],k["fingerprint"]) for k in json.load(sys.stdin)["keys"]]'
j $AUD $B/v1/keys -w "[%{http_code}]\n"
```

Expect:

```text
0 order-agent ['agent'] edba5bee3cb7
1 audrey ['auditor'] 5e36ca533901
2 alice ['approver'] 52513b4ee156
3 dana ['operator'] 568a2f681422
4 root ['admin'] 9a8e43fe03e4
{"error":"admin role required"}[403]
```

### 2.1 Create, use, expire and remove a key over the API

`POST /v1/keys` is admin only. The new key is shown **once**:

```bash
j $ROOT -X POST $B/v1/keys -d '{"name":"temp-auditor","role":"auditor","expires_in_days":1}' > try/ops/newkey.json
sed 's/"key":"[^"]*"/"key":"rv_…"/' try/ops/newkey.json
TEMP=$(python3 -c 'import json;print(json.load(open("try/ops/newkey.json"))["key"])')
curl -s -o /dev/null -w "the new key: %{http_code}\n" -H "Authorization: Bearer $TEMP" $B/v1/status
j $ROOT $B/v1/keys | python3 -c 'import sys,json;[print(k["index"],k["name"],k.get("expires_at")) for k in json.load(sys.stdin)["keys"] if k["name"]=="temp-auditor"]'
j $ROOT -X PATCH $B/v1/keys/$(kix temp-auditor) -d '{"expires_at":"2000-01-01T00:00:00Z"}'
curl -s -w " [%{http_code}] expired\n" -H "Authorization: Bearer $TEMP" $B/v1/status
```


### 2.3 Rotation and expiry by editing the file

Rotate "carol" without downtime: add her new key beside the old one, give the old entry an `expires_at`, and the server follows the file.
A file that does not parse is ignored and the old keys stay in force.

```bash
CAROL_OLD=carol-$(openssl rand -hex 8); CAROL_NEW=carol-$(openssl rand -hex 8)
cat > try/ops/keyedit.py <<'EOF2'
import json, sys, hashlib
f = "try/ops/keys.json"
ks = json.load(open(f))
mode, key = sys.argv[1], sys.argv[2] if len(sys.argv) > 2 else ""
if mode == "add":
    ks.append({"name": "carol", "role": "operator", "key_sha256": hashlib.sha256(key.encode()).hexdigest()})
elif mode == "expire-old":
    for k in ks:
        if k["name"] == "carol":
```

### 4.3 Verify the webhook signature

The `webhook` channel signs the body with HMAC-SHA-256 and sends `x-reversi-signature: sha256=<hex>`. The fake endpoint saved the last

```bash

import os
from reversi_sdk import verify_webhook_signature
body = open("try/ops/last-webhook.body", "rb").read()
sig = open("try/ops/last-webhook.sig").read()
secret = os.environ["HOOK_SECRET"]
print("genuine delivery:", verify_webhook_signature(secret, body, sig))
print("body changed:    ", verify_webhook_signature(secret, body.replace(b"approval_requested", b"approval_decided"), sig))
print("wrong secret:    ", verify_webhook_signature("not-the-secret", body, sig))
print("no header:       ", verify_webhook_signature(secret, body, None))
EOF2
```

## 8. Egress and data residency

Every outbound call Reversi makes (notifications, anchor webhooks, trace export, remote manifests, upstreams) passes the egress rules in
`reversi.config.yaml`. `allow` lists host patterns; unset means any host. `block_private: true` refuses loopback, private and link-local
addresses (off by default so local development works). Cloud metadata addresses such as 169.254.169.254 are always refused.
`region` is only a label: it appears in refusal messages, in signed anchors (section 6.4) and in the PDF report (section 6.2).

```bash
cat > try/ops/egress.yaml <<'EOF2'
manifests: ./manifests
policy: ./policy.yaml
data: { dir: ./data }
egress:
  allow: ["127.0.0.1", "169.254.169.254"]
  region: eu-west
notifications:
  channels:
    - { type: webhook, name: listed, url: "http://127.0.0.1:7811/webhook" }
    - { type: webhook, name: not-listed, url: "http://localhost:7811/webhook" }
    - { type: webhook, name: metadata, url: "http://169.254.169.254/latest/meta-data" }
EOF2
cat > try/ops/egress-private.yaml <<'EOF2'
manifests: ./manifests
policy: ./policy.yaml
data: { dir: ./data }
egress:
  block_private: true
notifications:
  channels:
    - { type: webhook, name: loopback, url: "http://127.0.0.1:7811/webhook" }
    - { type: webhook, name: lan, url: "http://10.1.2.3/hook" }
EOF2
```

`reversi doctor` checks every configured destination without sending anything:

```bash

rv --config try/ops/egress-private.yaml doctor | grep " egress"
```

Expect:

```text

FAIL  egress: localhost is not in the egress allowlist (region eu-west)
FAIL  egress: 169.254.169.254 resolves to a cloud metadata address (169.254.169.254), which is never allowed
FAIL  egress: 127.0.0.1 resolves to a private or loopback address (127.0.0.1) and egress.block_private is on
FAIL  egress: 10.1.2.3 resolves to a private or loopback address (10.1.2.3) and egress.block_private is on
```

## 9. The three stores, with the same scenario

The same four calls against each store: open a run, create an order, ask for a charge over 100 (blocked for approval), and try a tool out of scope.
Then a **second server on the same store** approves the charge and the first server lets it through, which shows that the ledger and approvals are shared.

```bash
scenario() { local B=localhost:$1 R=$2
  j $AGENT -X POST $B/v1/runs -d "{\"run_id\":\"$R\",\"permissions\":[\"orders:write\",\"payments:write\"]}" > /dev/null
  j $AGENT -X POST $B/v1/runs/$R/intents -d '{"tool":"create_order","args":{"sku":"B"},"reason":"order"}'
  j $AGENT -X POST $B/v1/runs/$R/steps/0/outcome -d '{"status":"succeeded","result":{"order_id":"o1"}}'
  j $AGENT -X POST $B/v1/runs/$R/intents -d '{"tool":"charge_card","args":{"amount":500},"reason":"pay"}' | cut -c1-90
  j $AGENT -X POST $B/v1/runs/$R/intents -d '{"tool":"delete_customer","args":{"id":"c1"},"reason":"x"}' | cut -c1-110
}
shared() { local R=$1 P1=$2 P2=$3
  ID=$(curl -s -H "Authorization: Bearer $APPR" "localhost:$P2/v1/approvals?status=pending" | python3 -c "import sys,json;print([a['id'] for a in json.load(sys.stdin)['approvals'] if a['run_id']=='$R'][0])")
  curl -s -X POST -H "Authorization: Bearer $APPR" -H 'content-type: application/json' localhost:$P2/v1/approvals/$ID/approve -d '{"note":"ok"}' | python3 -c 'import sys,json;a=json.load(sys.stdin);print("approved on the second server:",a["status"],a["decided_by"])'
  j $AGENT -X POST localhost:$P1/v1/runs/$R/intents -d '{"tool":"charge_card","args":{"amount":500},"reason":"pay"}'
  j $AGENT -X POST localhost:$P1/v1/runs/$R/steps/1/outcome -d '{"status":"succeeded","result":{"charge_id":"ch_1"}}'
}
ledgers() { for p in "$@"; do curl -s -H "Authorization: Bearer $AUD" localhost:$p/v1/ledger/verify | python3 -c "import sys,json;d=json.load(sys.stdin);print('port $p:',d['ok'],d['records'],'records, head',d['head'][:16])"; done; }
TAG=$(date +%s)
```

## Not covered here

- **Real third-party services.** Slack (including interactive Approve and Deny buttons), Teams, PagerDuty, Opsgenie, a real SMTP relay (STARTTLS, AUTH,
  implicit TLS), and a real OpenTelemetry collector. Only localhost fakes were used. The anchor webhook sink, remote manifest URLs and gateway
  upstream URLs through the egress guard were not run either.
- **Alerts that need time or a failure:** an unresolved step (needs more than an hour), approval timeout and escalation, a failed compensation, an unhealthy
  gateway upstream.
- **Browser sign-in with SSO redirects** (not built: the console takes a pasted key or token). The console was exercised with `curl`; nothing was clicked in a browser.
- **TLS and `REVERSI_SECURE_COOKIES=1`**, which need HTTPS in front.
- **Docker image build and run, Docker Compose, Helm (lint, template, install), the GitHub workflows.**
- **PostgreSQL over the network, with TLS, or with a restricted role;** append-only triggers were not provoked.
- **A Terraform provider and a Kubernetes operator.** They are not built; use `reversi apply` and the Helm chart.
